# basic-pitch 推理放到 Web Worker

背景：168 秒真实钢琴曲加载后，basic-pitch 在主线程推理，实测出现最长 16 秒的帧间隔；提取完成后播放恢复 60fps、JS 堆约 338MB。用户感知为“播放一段时间后浏览器特别卡”。决定：把模型推理放到专用 Web Worker；主线程只做 22.05kHz 高质量重采样、onset 精修与结果应用。提取期间 UI 保持可交互，可播放/调参/换歌/取消；新加载或取消会终止旧 Worker。提取完成时若正在播放，先缓存为“待应用旋律”，暂停/seek/播完再应用，避免正在播放的画面跳变。Worker/模型失败时回退到 FFT 旋律（自动模式回网格）。

备选方案：改成按需提取（切玻璃/音符模式才跑）——加载快，但触发时仍会在主线程卡；主线程分块让路——大冻结变小卡顿，但总 CPU 不变且分块边界可能影响音符精度；关掉 basic-pitch 用 FFT——不卡，但会退回音符同步质量较差的状态。

## 后果

- Worker 固定 CPU 后端（TFJS 3.21 的 WebGL 后端在 Worker 里引用 `window`，不可用），总提取时间可能比主线程 GPU 更长；UI 不再被模型阻塞。
- 需要手动重采样、Worker 消息协议、终止/取消与“待应用旋律”状态。
- 玻璃整轨渲染仍是独立的性能点；本次只解决模型推理的主线程阻塞。
- 真实曲验收以主线程帧间隔、提取完成后的音符/图表、换歌/取消、暂停/seek 应用为准。
